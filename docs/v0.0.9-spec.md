## 4. Windows 桌面应用

### 4.1 实现方向

工程默认先评估并锁定 Electron，目的是复用现有 TypeScript／Node 应用服务，而不是同时再引入一套 Rust 后端。此项不是已安装依赖或实测性能结论。精确版本在依赖可获得性、内嵌 Node、SQLite、官方 MCP SDK 与 keyring 绑定兼容检查后确定。

使用本地打包页面、隔离的 renderer、最小 preload 白名单和受验证 IPC。数据库、凭据解析和运行器留在宿主／受控应用进程中。renderer 禁止 Node 集成，不暴露任意 IPC、shell、SQL、路径读写或 Git 接口。验证发送者与输入 schema，拒绝不可信导航／子窗口，不执行稿件中的 HTML、脚本或外部图片。

Electron 官方安全指导要求上下文隔离、沙箱与 IPC 发送者校验；原生 Node 模块还需要按 Electron 环境验证或重建 [E1][E2][E3]。所以在系统 Node 24 上能加载 keyring，不代表打包后的桌面应用已经能加载。

先完成应用数据和凭据 namespace 兼容，不能因新壳自动复制用户所有工作区或产生第二份无提示凭据。

### 4.2 使用场景

打开／创建独立写作工作区，导入文章或创建任务，选已有预设与写作档案，批准阶段，查看进度与候选，阅读引用与语义意见，进行范围级采用／拒绝／撤回，导出。

正文居中且优先占空间；左侧文章／任务导航，右侧可收起的审稿／来源／意图区。界面中英双语。没有实现的能力不提供假按钮；只读 HTML 报告继续保留为独立快照，不拥有后台修改权限。

长任务、同步 SQLite 和重型索引不阻塞界面。关闭窗口时明确提示停止／退出的含义，不默认变为常驻后台服务。崩溃后的已保存任务沿用现有恢复规则，未保存字符不承诺全部恢复。

### 4.3 分发验收

交付桌面源码、可复现构建配置、Windows 安装／便携发行产物及安装测试说明。目标是终端用户无需另行安装 Node、Git 或开发工具；开发集成器的依赖与普通应用不同。

测试安装、启动、升级保留数据、卸载是否保留私稿、中文路径、用户级写权限、MCP 子进程关闭和原生绑定。签名、Smart App Control／SmartScreen 表现分别报告；无可信签名的产物不得宣称已签名或保证免拦截。不能以关系统保护、改扩展名或复制快捷方式代替发行信任。

## 5. 范围级编辑：是真正的操作单位

### 5.1 数据和兼容

复用正文版本、稳定块 ID 和历史，不按每次输入重新切全文／重建所有 ID。增加有版本的范围操作契约：operation ID、所属候选及基线 revision、block ID/version、UTF-16 范围、精确原文和替换文本、必要的上下文身份、依赖／互斥／原子组。

UI 可以按句子或词展示，持久身份依靠范围、版本和操作记录，不依赖模型自报句子号。坐标不能切开 surrogate pair 或 grapheme；规范化仅用于显示／查找，不能修改存储原字节后还沿用旧坐标。

旧 Proposal v1 和历史状态继续可读；新范围集合的“部分采用”状态是新的明确语义，不能把只接受一个子操作标成整块提案已接受。旧块级提案可在新的作者审查操作中转换出范围候选，固定转换算法／基线并再次核对，不追溯性改写旧历史。

### 5.2 采用、拒绝与撤回

一个替换由删除与插入组成时应作为同一可理解操作，不把纯算法 diff 的每个字符片段都当成可以任意组合的作者决定。

- 互不重叠且无依赖的操作可以分别采用／拒绝；通过已记录的变化映射准确更新位置。
- 同一基线上的候选不能在原文改变后靠旧 offset 直接落地。仅在完整变更链可验证且不相交时重映射；歧义、历史缺失或重叠要停止并显示原因。
- 重复句子不能通过全文第一次匹配猜测落点；插入点左右偏向及同位置多插入顺序明确。
- 撤回创建一个新的补偿版本，仅针对该操作产生的可追踪内容；不恢复整个文档快照。
- 后续操作改动了同一区域时，显示依赖／冲突；由作者选择有序撤回相关操作或提出新修改，不自动抹掉后续工作。
- 保存人工编辑、自动保存缓冲、批准 AI 与撤回已批准修改是不同动作。自动保存不是批准候选。
- 一次批量确认使用短事务，成功全部落盘或整体回滚；网络等待不处于写事务中。

基础验收必须包含：同段两处独立修改，只接受其中一处；两处都接受后只撤回第一处，第二处保持；后续人手编辑了撤回区域时正确拒绝直接撤回。不能用仅高亮到词、按钮仍按整块处理的 B 方案交付来冒充 C。

首版至少完整支持现有稳定文本块内的插入／删除／替换，以及有清楚边界的多操作组。不声称提供任意富文本结构、实时协作或无冲突的跨段重排。会改变块身份的拆分／合并／移动需独立操作契约；未实现时必须在执行前明确限制，不误映射已有来源。

### 5.3 审稿与来源

显示机械 diff、可争议的模型意见与作者反馈。引用与论断关联固定对应版本；受到影响的范围标为需要核查，无法安全精确证明无影响时保守过期。位置映射正确不等于观点没变或来源支持新表述。

缓存 key 固定输入版本／算法，计算有大小和时间预算。降为较粗显示可以明确说明，但不能因此取消采用／撤回的安全检查。

## 6. Updater v0.2：独立面板和 worktree

保留上一版规划的全部恢复、包校验、CI、日志与保护要求，并将其从推荐提升为必需验收。

独立本地浏览器面板使用 loopback、会话认证、Host/Origin/CSRF 校验和受限路由。固定入口启动的只是这个进程，不自动安装服务或扩大监听范围。运行过程不暴露任意命令终端或所有磁盘文件接口。写作应用不能通过共用前端代码获得其会话权限。

每次集成使用自有持久目录下的唯一 worktree／分支。用 Git 接口定位 common directory，支持 .git 是文件；共享仓库写操作加锁，不抢其他进程的 lock。原目录未提交内容和 index 不受导入影响。worktree 共享对象与部分配置，不是恶意代码沙箱。

同一任务按 prepared/applied/local-validated/committed/pushed/pr-created/ci-waiting/merge-requested/merged/local-sync/done 保存结构化状态。包、测试环境、实际树和外部结果相互固定；不是从日志字符串猜下一步。

推送／创建 PR／合并响应丢失后先只读核对；未知就暂停，不猜失败后再次执行。状态分别显示远端合并、本地同步、验证和清理。原目录不在目标分支、不干净、有独有提交或不能快进时，只提示待同步，不自动 stash/reset/切换用户分支。

清理只删除能够证明归属且未被改变的任务分支／worktree。清理失败是警告，不撤销已确认的远端成功。源码集成失败不操作私人工作区 schema。

## 7. 仓库更名适配：稳定身份优先

### 7.1 核心契约

RepoIdentity 使用已批准 GitHub 主机＋数值 repository ID；node ID 可用于官方 GraphQL 节点查询。owner ID 单独保存用于识别所有权变化，full_name/clone URL/default branch 是从该身份解析的可变元数据。不得将 URL 名称相等视为身份相等，也不能把产品显示名作为安全判据。

本项目首次迁移目标是 github.com / 1370967185。先通过用户现有认证验证，保存本机信任映射。GitHub 将 repository ID 作为不可变身份，与可复用名称区分 [G3]；官方 GraphQL 支持以 global node ID 查询对象 [G4]。实际集成使用稳定身份解析当前名称，不要求旧路径必须仍重定向。

每次开始、续跑、推送、创建 PR、合并、查询／下载 Release 前重新解析身份。通过官方 API 获取 canonical full_name 与当前 URL，再调用相应接口，操作后核对返回的目标与对象 ID。

### 7.2 名称变化的默认处理

同一 repository ID、同一 owner ID、主机／目标分支／权限／基线均仍适用时：记录更名事件，更新当前显示名称与地址，继续原任务。该兼容策略由用户在 v0.2 配置迁移时批准，不为每次合法更名要求重建项目、重填 Key 或重新下载同一包。

元数据更新是可重试的读操作；远端写入若刚好跨越改名且返回不明确，仍先对账。不能承诺并发改名和网络中断时毫无暂停，也不能仅用一次预检声称所有后续写入都具有按 repo ID 的原子锁。

更新器在迁移同意范围内可以修正其管理的 remote 地址。由于 worktree 共享 Git 配置，应优先使用更新器命名的专用 remote／显式经验证 URL，避免不经说明更改作者维护的 origin。作者允许管理 origin 时，只替换已绑定目标；自定义 pushurl、SSH 别名、多个 remote、用户在执行间更改的地址需单独核对，不能全局替换所有 Git URL。

### 7.3 不应该自动跟随的变化

- 删除后重建同名仓库、fork／mirror、不同 repository ID：暂停并要求作为新目标重新绑定。
- 转移到不同 owner ID、不同 GitHub 主机：重新确认所有权、权限与发行信任；不能只因 repo ID 未变就自动把代码交给新所有者。
- 仅 owner 登录名改了但 owner ID 未变：可以按名称变化更新，仍校验现有权限。
- 默认分支变了：新任务可以预览新默认值；进行中的已批准目标分支不自动改投另一分支。
- 私有化、被归档、权限丢失、令牌过期、API 不可达：按真实状态暂停；404 不能直接断言仓库已删除。
- 旧 URL 被新仓库占用：继续按原稳定身份找原库；严禁把旧名的新库当成原目标。

### 7.4 改名影响的每个对象

本地任务/缓存/worktree 使用 repo ID 与 task ID 的稳定路径；不跟着 slug 批量移动磁盘目录。PR 保留仓库身份＋PR 编号/ID；Release 保留 repo ID＋release/asset ID；CI 保留 run/check ID 与实际提交。更名后按当前地址构造链接，历史事件保留当时地址。

源码包清单的 repository 字符串成为定位提示／历史名称，而不是唯一身份验证；新包应附结构化 repo identity。基线 commit/tree、完整变更集、文件哈希、包修订及批准记录仍必须核对。仓库改名不意味着可以导入过期基线或任意历史包。

旧 format-1 包仅在可信本机迁移关联或经过验证的现存目标映射下兼容读取；没有稳定 ID 的未知旧包不能仅按白名单名称放行。原包保持原始字节，不为改名重新写包内 manifest／哈希。不执行旧包内硬编码名称的 apply 脚本；v0.2 由自己的 guarded importer 使用数据清单。

是否将身份放在兼容扩展字段或外层版本化描述中，在实际解析器检查后确定并形成明确格式版本。优先保留 format-1 核心契约，但不得宣称 v0.1.2 已获得改名能力，也不得为兼容旧解析器去掉身份保护。

### 7.5 GitHub 自带重定向不能替代此设计

GitHub 通常重定向仓库网页与 Git 操作，但项目站点 URL 和引用被更名仓库所托管 action 的调用存在例外，复用原名还会破坏原重定向 [G2]。因此必须按身份重新解析，不依赖旧 URL 永久正确。

对于已托管的 README/badge、发布配置、外部 action 使用者、GitHub Pages、自定义域、OIDC／外部系统信任及 npm 包名，更新器只在自己的范围内动态更新地址。不会保证外部服务的所有硬编码链接自动修复。必要的仓库文档／CI 变更走源码修改；第三方设置列出提示，由作者批准。历史记录不重写。

## 8. GitHub Release 下载与发行类型

Release 是本地 ZIP 之外的额外渠道。新源码尚未进入远端时仍可由作者提供 delivery 包，不制造“先从同仓库下载尚未上传版本”的循环。

Release 来源先按已批准 repo ID 解析；独立保存 release ID、asset ID、资产类型、应用版本、目标平台／架构、大小与校验值。包类型至少区分源码交付、Updater 引导包和 Windows 应用安装包；不能把安装器当源码清单导入 worktree，也不能把依赖准备结果包当应用更新。

没有 Release 时显示无发布版本，不把 main 当成一份安装包。区分 stable/prerelease 与 Siglum/Updater 两条版本流；不可仅用 GitHub latest 或最高 tag 字符串混排。下载后先校验，再请求具体执行权限；下载本身不等于安装、合并或发布。

同版本不同哈希/asset 更新视为不同修订，不能静默覆盖已批准缓存。任务固定批准时的精确包。服务资产必要的下载跳转要受控，不能把认证头带到未批准的目标。哈希是内容一致性，不等同于发布者签名；签名／attestation 如实现，必须核对独立信任根和实际发布者身份。

Updater v0.2 不自动修改 GitHub 仓库名或发布新 Release。面板可提供打开当前仓库设置和重新核对的入口；真正 rename/publish 是另一次明确写操作授权。

## 9. CI、包与运行保护

沿用已选包缓存、ZIP 路径／大小／重复名／Windows 保留名／大小写冲突和链接检查。包内不能自行降低测试配方。构建测试需要执行项目代码，不是沙箱；子进程使用最小必要环境，不继承无关 API Key／GitHub token。

预期 CI 集合由受信任项目策略确定，当前为 Ubuntu/Windows × Node22/24；核对提交、工作流来源与全部必需成功。缺失、跳过、中立、取消和超时不算必需项成功。保留精确 PR head 核对；再次检查 base 漂移，不静默 rebase/强推。

推荐服务端 strict required checks／merge queue；实际启用另行授权。客户端预检无法代替服务端原子合并门禁。已合并版本再次运行只读展示，不重复集成；后来被 revert 的历史合并不能等同于该功能现在仍在主线。

第一次安装 v0.2 的独立引导包迁移旧仓库位置与偏好，复用 GitHub CLI 身份，不复制其 token。程序、自身配置与任务状态放在稳定 Known Folder，而不是 Downloads。自更新使用版本化目录，不能覆盖正在运行的代码；保留旧版可回退入口，配置迁移不可无备份破坏旧状态。

## 10. 发布前顺序与改名时机

1. 先验证新增桌面／编辑依赖可实际安装，解析 API、原生 ABI、许可和冻结锁文件。
2. 实现 Updater v0.2 的稳定身份、原生清单导入、缓存、worktree 与完整恢复；以隔离测试验证多次改名、旧名复用和未知结果。
3. 实现范围操作核心及回归，再将其接入桌面界面；不要先做看起来可点击但无法安全落地的按钮。
4. 完成 Updater 独立面板、Release 资产识别和 Windows 安装／启动／退出测试。
5. 产生 Siglum 源码交付、桌面安装产物和 Updater 独立引导产物，各自标明用途、基线和真实验证范围。
6. 先迁移并验证 v0.2，再由作者确定最终仓库 slug 并明确执行 GitHub 更名。更名后 v0.2 按稳定 ID 验证，继续同一项目，不要求手工修改源码包。

如果作者在 v0.2 之前已经改名，停止让 v0.1.2 盲目重跑；新引导器根据已知 repository ID 恢复绑定并解释结果。不能把旧版本的硬编码失败当成要求关闭新保护的理由。

开发交付仍以本轮真实 main 为起点；开发结束前再解析 repo ID 和主线。纯改名不改变待交付代码树的检查要求；有新提交则重新核对基线，不能用名称变化掩盖提交变化。

## 11. 联合验收矩阵

### 桌面／范围编辑

中文 IME、粘贴、Emoji/组合字符、CRLF、空文稿与长段落；缓冲落盘与重启恢复；同段多操作的不同接受顺序；独立撤回不破坏其他改动；重复文本与插入点；同范围互斥；人工修改与模型迟到；原子组回滚；旧文档和 Proposal v1；引用／语义分析随范围和版本失效；渲染恶意 Markdown 不执行；renderer 不取得 Key/Git/任意文件能力。

Windows 实际应用启动、安装/卸载/升级、打包 Node/SQLite/keyring/MCP、路径空格／中文、直接子进程退出、窗口关闭和已有任务恢复单独报告，不拿浏览器测试或系统 Node 测试替代桌面证据。

### 仓库身份／Updater

首次按旧名绑定；从旧名改为新名、连续多次改名、改回旧名、只改大小写；提交前／推送后／已有 PR／等待 CI／合并响应丢失时改名；原名被另一个 ID 占用；fork 或删除重建；owner 登录名改动及 ownerID 转移的区别；main 变更／无权限／API断网；旧包历史名称但真实身份与基线匹配；新名字但错误 ID；SSH/HTTPS/custom pushurl；Release 变更名称但原 asset identity 可追踪；半途下载；同版本修补包；用户原目录不干净；Windows worktree路径；清理失败。

正式的改名测试使用隔离且获准的测试仓库或明确标记的模拟 API。未经作者授权不能改名生产仓库来“验收”；模拟通过不能声称已经完成真实 GitHub 改名验证。

### 验证与用户操作

将源码冻结安装/回归、桌面运行、Windows 原生组件、GitHub CI、真实改名、Release 下载、真实模型／搜索效果分别报告。未运行就是未运行。没有真实签名就明确未签名。CI绿、main合并、Release存在、应用安装和功能实测是不同事实。

日常目标是固定入口、自动识别、一次范围确认、失败后点击继续；不要求手工复制文件、改清单、清理仓库、重复登录或关闭 Windows 安全措施。
