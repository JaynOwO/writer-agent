# v0.0.1 acceptance specification

## Scope

Deliver a runnable local revision-engine preview, not an AI editor mockup. Required modules are core, storage, models (scripted mock), CLI, documentation and tests. No graphical UI, cloud inference, browser research, paid API dependency, vector store, real memory learning, MCP or Skills execution.

## Acceptance criteria

- A new empty directory can be initialized, closed and reopened as a workspace.
- Multiple documents can be imported and exported without changing their unmodified text bytes.
- Proposals expose an immutable base revision and stable target block identifiers.
- Proposal validation is atomic. Invalid or stale batches save no changes.
- Different blocks can be accepted independently and in any order.
- Rejecting stores the reason without changing document text.
- Reverting one accepted change preserves unrelated accepted edits and appends history.
- Same-block interference and ABA are rejected explicitly.
- A simulated SQL failure cannot leave a half-applied decision.
- Schema mismatches, missing documents, no-op edits and illegal state transitions return errors.
- The scripted demo completes offline and exports final Markdown.
- `pnpm typecheck`, `pnpm test`, `pnpm demo` succeed after a normal dependency install.
- The initial integrator generates and commits a genuine `pnpm-lock.yaml` using pnpm; CI then uses frozen installs.

## Explicit granularity and data limits

The unit of review is one blank-line-segmented text block, not individual words or sentences. At most 100 different target blocks per proposal; at most 10,000 blocks and 2,000,000 UTF-8 bytes per document. A single revision does not batch-accept several edits; every accepted/reverted edit receives its own revision.

No automatic source-support verdict or author-intent verdict may be displayed. Human review is still required. Passing the rule fixtures proves implementation consistency for those examples only, not model quality or general semantic accuracy.

## Handoff boundary

The author delivers source files and test evidence. Spark imports them on a feature branch, performs an actual pnpm install, reruns validation, reports mechanical fixes, then commits/pushes/opens a PR when allowed. It must not merge or silently rewrite the project. User data must stay out of commits.
